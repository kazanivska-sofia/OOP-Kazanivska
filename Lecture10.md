# Доповідь: Оптимізація LINQ: Avoid multiple enumeration, PLINQ

# 1. Проблема множинної ітерації (Multiple Enumeration) та як її уникнути

Множинна ітерація виникає через відкладене виконання (Deferred Execution) у LINQ. Коли ми звертаємося до однієї й тієї ж змінної IEnumerable<T> декілька разів, LINQ виконує увесь запит спочатку при кожному зверненні. Це призводит до зайвих обчислень або повторних запитів до бази даних.

Проблемний приклад (запит виконується двічі):

```csharp
var expensiveQuery = GetProducts().Where(p => p.Price > 100);

// Перше виконання запиту:
Console.WriteLine($"Кількість: {expensiveQuery.Count()}");

// Друге виконання запиту:
foreach (var item in expensiveQuery)
{
    Console.WriteLine(item.Name);
}
Як уникнути проблеми:

Потрібно матеріалізувати запит (виконати його один раз) за допомогою методів ToList() або ToArray(), зберігши результат у пам'яті.
```

```csharp
// Запит виконується один раз і зберігається в списку:
var expensiveItems = GetProducts().Where(p => p.Price > 100).ToList();

Console.WriteLine($"Кількість: {expensiveItems.Count}");

foreach (var item in expensiveItems)
{
    Console.WriteLine(item.Name);
}
```

# 2. Коли доцільно використовувати PLINQ, а коли — ні

PLINQ (Parallel LINQ) — це паралельна реалізація LINQ, яка розбиває колекцію на частини та обробляє їх паралельно на кількох ядрах процесора за допомогою методу .AsParallel().

Коли PLINQ доцільний:

Великі колекції: Коли кількість елементів обчислюється сотнями тисяч або мільйонами.

Важкі обчислення: Коли операція над кожним елементом вимагає значних ресурсів процесора (наприклад, математичні розрахунки, криптографія, складне розпізнавання).

Коли PLINQ НЕ доцільний:

Малі колекції: Накладні витрати на створення та координацію потоків будуть більшими, ніж користь від паралелізму.

Операції введення-виведення (I/O): Звернення до баз даних, файлів або мережевих запитів краще робити через async/await, а не PLINQ.

Прості швидкі операції: Просте фільтрування чи додавання чисел у звичайному LINQ виконається швидше.

Приклад порівняння:

```csharp
List<int> numbers = Enumerable.Range(1, 10_000_000).ToList();

// Послідовний LINQ:
var sequentialResult = numbers
    .Where(n => n % 2 == 0)
    .Select(n => Math.Sqrt(n))
    .ToList();

// Паралельний PLINQ:
var parallelResult = numbers
    .AsParallel()
    .Where(n => n % 2 == 0)
    .Select(n => Math.Sqrt(n))
    .ToList();
```

# 3. Потенційні проблеми при використанні PLINQ

При використанні PLINQ виникають ризики, пов'язані з паралельним виконанням коду:

Зміна порядку елементів: За замовчуванням PLINQ не гарантує збереження початкового порядку елементів. Якщо порядок важливий, необхідно додавати метод .AsOrdered(), що може трохи знизити продуктивність.

Побічні ефекти (Side Effects): Якщо всередині лямбда-виразу змінюється спільний стан (наприклад, модифікується спільний список чи змінна), виникає стан гонитви (Race Condition).

Потокобезпечність (Thread Safety): Методи, що викликаються всередині PLINQ, повинні бути потокобезпечними. Не можна використовувати звичайні колекції на кшталт List<T> для запису з кількох потоків одночасно без блокувань (lock) або використання ConcurrentBag<T>.
